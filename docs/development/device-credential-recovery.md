# 管理员补发设备接入凭据

关联 [#42](https://github.com/yanghan24/xiaozhi/issues/42)。本文描述服务端候选实现；真实 P4 固件修改、身份保留及写回验收留到设备所在电脑继续。首次交付仍使用[交付协议](device-delivery-v1.md)。

## 授权与状态

补发的创建、查询、完成均要求正常运营管理员登录，并再次检查账号启用及超级管理员身份。一小时工具 token、长期烧录凭据、客户登录和设备接入凭据均不授予补发权限。本版没有向普通烧录工具委托补发的接口；管理员在受信工作站操作，将返回 identity 交给核对过的现场写入流程。

创建补发时立即替换同一 `dc_device` 的 credential hash，增加 revision 和 permission_version，失效旧绑定请求。原交付操作、P4/C6 硬件映射、板型、客户归属、ownership_version、准入及本地调用许可保持原值；已退出的设备仍退出，不撤销同账号其他设备的集市授权。旧语音令牌及会话在现有服务端闸门检查时被拒绝；本轮物理停播时延尚未验收。

创建后旧凭据立即失效，写回前设备可能暂不可用。只有核对真实设备与维护窗口后才执行。恢复既有客户使用状态与首次准入不同，补发完成只登记写回结果，不启用设备或绑定客户。

## HTTP 契约

路径前缀 `/xiaozhi/device-delivery/v1`；要求 HTTPS、JSON v1、无 query、单值身份头及 `Cache-Control: no-store`，沿用 4 KiB 请求限制。操作号为 32 位小写十六进制。

| 接口 | 请求 | 行为 |
| --- | --- | --- |
| POST `/recoveries` | 管理员 Bearer、`Idempotency-Key`；`version:1`、`device_id`、`previous_operation_id` | 原子补发，返回操作元数据及六字段 identity |
| GET `/recoveries/{id}` | 发起该操作的管理员 Bearer | 当前补发元数据，不含凭据 |
| POST `/device-check` | 新设备凭据、Device-Id；version、P4/C6 硬件标识 | 核对原硬件映射，记录当前补发设备验证时间 |
| POST `/recoveries/{id}/complete` | 发起该操作的管理员 Bearer；`version:1`、`write_operation_id` | 设备验证完成后登记写回回执，返回不含凭据的元数据 |

`previous_operation_id` 是当前凭据所属的首次交付或上一次补发操作号。现场私有 journal 必须先保存新的补发操作号与写入操作号；响应丢失后使用相同参数重试。两次不同补发竞争同一前驱时仅一项成功，其余返回 409；同一操作重试返回相同凭据。管理员更换登录 token 后可续作，但须为同一管理员账号。

identity 与首次交付六字段格式一致：version、hardware_id、device_id、credential、ota_url、control_origin。OTA origin 来自后台配置。原交付记录的密文保留审计，但凭据轮换后不能重放取回，旧 complete 也不能重新启用设备。下一轮补发后，前一轮补发的重放、查询及迟到 complete 返回 409；旧设备检查返回 401。尚未首次完成交付的设备应继续原交付操作，不通过补发绕过首次准入。

## 存储与事务

新增 `dc_device_recovery` 保存前驱操作、管理员、设备、凭据 hash/AES-GCM 密文、验证及完成时间。复用交付加密密钥，AAD 绑定补发操作号、设备和管理员。服务重启必须保留数据库和原密钥。

创建按身份全局 barrier → 设备行 → 操作行加锁，与归属/许可事务保持顺序。设备检查和完成按设备行 → 操作行；完成不会反向申请 barrier。新凭据、版本变更和旧请求失效在同一事务中提交。归属和集市授权记录不被补发更新。

## P4 接续与维护边界

用户于 2026-11-11 确认稍后在 P4 所在电脑继续实机。设备现场基点见[双机交付记录](../verification/2026-11-11-two-device-delivery.md)：应用 `2.2.6 / 00896ab`，P4 rev 3.2、32 MB 物理 Flash、原 16 MB 布局。当前电脑没有该完整固件 checkout、实际 sdkconfig、烧录分区及 P4；仓库中的历史固件片段不能作为此版本实现依据。

| 操作 | #42 要求的行为 | 尚需核对及实现 |
| --- | --- | --- |
| 应用槽重刷 | 保留稳定身份和凭据 | 核对写入地址、长度及身份存储不重叠，前后读回 |
| OTA | 保留身份和凭据 | 核对实际 OTA 与分区兼容路径、升级及重启 |
| 重新配网 | 只清理网络配置 | 追踪实际 Wi-Fi 清理 API |
| 正常恢复出厂 | 清理普通配置，保留设备身份 | 找出所有恢复入口及清理范围 |
| 普通 NVS 初始化失败/修复 | 不误清身份 | 检查 `nvs_flash_erase` 等整分区清理及错误分支；独立命名空间本身不隔离整分区擦除 |
| 全片擦除或身份异常丢失 | 停止使用旧身份，由管理员授权恢复同一档案 | 在可恢复备份及固定产物齐备后执行，记录补发写回及重启 |

在固件工程实际基点选择持久化方案；若增加独立身份分区，须证明当前已烧录布局的兼容与迁移，不能仅修改未启用 CSV。迁移成功前保留可恢复的旧身份材料，失败时关闭接入，不自动登记第二档案。旧私有 journal 中的身份不得覆盖已补发身份；现场写入流程须先核对当前补发代际与后台响应。

固件工程还须实现/核对实际写回与续作路径，再采集：每种正常维护前后身份指纹一致、异常丢失后关闭接入、管理员补发写回、新凭据可用/旧凭据拒绝、原归属及退出状态保持、设备重启结果。公开证据只记录别名、版本、摘要与状态；身份、秘密、整片 Flash 和原始串口日志留在受限目录。

当前没有证据证明已启用 eFuse 秘密保护、Flash/NVS 加密、Secure Boot 或秘密不可提取。服务端加密存储不构成设备物理保护。

## 部署与回退

先在隔离 Ubuntu 数据库运行回归，再按[当前部署入口](../deployment/current.md)核对实际服务并备份必要身份数据和密钥。新增 recovery 精确入口随 API 同步部署；本文没有更改现场部署状态。

停止新补发时撤回 recovery 路由，保留支持新凭据的 device-check 和现有控制服务。代码回退不恢复旧凭据；退回不理解补发的旧 API 会使已补发设备的 device-check 失败。保留新增操作表、归属、当前 hash 和原加密密钥，恢复支持补发的服务版本。不得通过回滚数据库秘密、删档或重跑旧 complete 恢复服务。
