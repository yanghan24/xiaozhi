## 结论与证据

需要修正授权生命周期、退出和多设备验收。建议首版继续采用已确认的“小智绑定页 → web OIDC → 后端保管令牌和 Key”，加入自动续期及主动撤销。新增设备授权是可选路径；它不提供硬件身份和设备管理，不能自动替代 [ADR-0003](../adr/0003-oidc-web-login-for-device-binding.md)、[ADR-0005](../adr/0005-backend-owns-device-management.md) 的职责安排。

## 必须修正的接口事实

下表节号均对应新文档。

| 事项 | 旧资料或现有待确认项 | 新文档事实 | 对小智的影响 |
| --- | --- | --- | --- |
| 长期授权 | 不提供刷新令牌 | 管理员允许且用户同意 `offline_access` 后签发 Refresh Token；web 首次申请使用 `prompt=consent`（§3.3、§4.4） | 登记和申请 `openid profile credentials:manage offline_access`；按实际获准范围处理，首次用户同意仍必需 |
| 刷新生命周期 | 缺少自动续期路径 | Access/ID Token 为 5 分钟；Refresh Token 每次轮换，连续 30 天未刷新失效，持续刷新无固定累计期限（§4.4） | 后端安全保存和更新令牌；需要有效 Access Token 时刷新，活跃授权在闲置期前续期；模型调用本身不会完成刷新 |
| 模型 Key | 与来源网页登录寿命关联 | `expires_at: null` 表示无固定到期时间；网页、原始集团凭证或 Refresh Token 的自然到期不自动撤销 Key（§4.4、§7.2） | 接受空到期时间；分开处理本地调用许可、刷新能力和上游 Key 状态；不能将五分钟当成音箱退出倒计时 |
| 刷新并发及失败 | 未要求轮换保护 | 旧刷新令牌重放会撤销关联授权；保存失败不能回退旧值；网络/5xx 不等于退出（§4.4） | 同一刷新链串行，覆盖多实例和重启；新状态原子保存，响应丢失避免盲目重放；临时错误不直接删除 Key |
| 退出 | 需实现退出即停止 Key，撤销契约未完整取得 | OIDC 退出和清除本地会话均不自动撤销长期授权；新增 `DELETE /api/oidc/authorization`（§5、§7.4） | 小智先停止新调用，再用有效 Access Token 撤销应用授权；成功后清理令牌/Key，失败记录远端撤销未完成 |
| 多设备 | 同账号可能共用 Key | 明确按用户和接入应用共享 Key；撤销应用授权影响该用户同应用其他终端（§7.2、§7.4） | 账号级退出与单台停用/解绑必须区分；不能通过撤销共享授权实现仅一台音箱解绑 |
| 在途请求 | 取消语义待核实 | 撤销只阻止后续新请求；已受理请求继续完成及结算（§7.4） | 本地立即停播、停止追加文本并丢弃迟到结果；上游取消仍按规范通/TTS 各自接口处理 |
| 设备授权 | 只有 web/spa/native | 增加 RFC 8628 设备授权，device 客户端不使用 Secret、不登记回调或注销通知（§1.1、§8） | 可评估新扫码路径；采用它需重审凭据保管、后端身份关联和退出通知方案 |

最低 scope 建议继续不包含 `balance:read`：首版没有绑定时查询余额或本地结算需求。示例中的 scope 全集不是所有接入方都必须申请的范围。

## 建议的生命周期实现

下列是基于已确认产品行为的实现建议，尚未编写功能代码。

1. 分别维护设备归属、本地调用许可、OIDC 会话和独立应用授权、刷新令牌、共享 Key。设备已绑定不等于允许调用；Key 尚可用也不能绕过“未登录或已退出不得使用 Key”的产品规则。浏览器自然到期、短期令牌到期与显式退出分别处理。
2. 刷新按授权链互斥，避免多设备或服务实例同时使用同一 Refresh Token。新令牌成功持久化后才对调用方生效；保存失败、响应丢失和进程重启有明确恢复状态。文档中的进程内 `refreshing` 示例不能直接代替跨实例协调。
3. `invalid_grant` 转入需要重新授权的处理，不能仅凭此错误认定 Key 已被集市撤销：它可能只是刷新令牌闲置到期。本地是否允许继续调用仍取决于已确认的登录/授权规则，不因持有 Key 自动恢复。
4. 用户在小智侧退出时，立即持久化禁止新调用的状态，并使所有使用该授权的语音任务停止本地输出。随后使用有效 Access Token 请求 `DELETE /api/oidc/authorization`；必要时先完成一次受控刷新。远端撤销完成前保留仅供撤销处理使用的受保护凭据，不能先删除所有凭据再尝试撤销。
5. 撤销失败时仍保持本地停用，记录“本地已退出、远端撤销待确认”。退出与再次登录需要串行或版本保护；旧撤销重试不得误撤销后来新建的授权。若两种令牌都已失效，新文档没有给出以 Key 或 Secret 代替 Access Token 撤销的办法，需重新认证或确认集市侧恢复渠道。
6. 保留 `DELETE /api/application-credentials` 作为只撤销 Key 的不同操作。完整退出使用应用授权撤销，避免剩余 Refresh Token 仍能领取新 Key。单台解绑只改变小智的归属及设备调用许可，并清理该设备旧上下文，保持其他设备的共享授权。
7. 验证 Back-Channel Logout 的签名、`sid/sub`、`jti` 及新旧会话关联；自然超时或网络故障不能伪装成显式注销。新文档说明通知失败时不保证即时到达，且 OIDC 退出不等于微信、集团或集市网站全局退出。

## 是否切换设备授权

建议本轮保留 web 路径。后台统一保管 Key、原账号在手机页面重新认证后解绑、同账号多设备控制已经写入规格 #10/#13/#15。新增 `offline_access` 在 web 路径同样可用，因此长期使用并不依赖切换到 device。

若选择第 8 节的设备流程，需要先明确以下变化，再更新 ADR 和相应验收项：

| 设备流程事实 | 对现有方案的额外工作 |
| --- | --- |
| 一个 Client ID 代表整个设备应用，客户端类型创建后不可修改（§1） | 不能为每台音箱建 Client ID，也不能假定当前 web Client ID 能用于 device grant；需登记正确类型 |
| 二维码使用实际返回的 `verification_uri_complete`，同时显示 `user_code`，`device_code` 私密保存；示例有效期 600 秒（§8.1） | 固件需支持码展示及过期处理；不得把私密设备码、Key 放入二维码 |
| 按 `interval` 轮询，遇 `slow_down` 本次及后续间隔增加 5 秒，成功只领取一次（§8.2） | 实现等待、拒绝、过期、减速和超时退避；遵循实际返回时长 |
| 申请和核对入口单 IP 每分钟 120 次，设备码另外限制轮询间隔（§8.2） | 同一出口批量配网需错峰；不能把此限制误写成所有 token 轮询或模型调用的额度 |
| 设备类型不登记注销通知地址（§1.1） | 不能沿用 web 回调/通知假设来保证手机退出立即停用；需另有服务端控制与状态传播 |
| 集市不包含硬件序列号认证及单台管理（§8.3） | 小智仍须证明具体设备来源，关联可信授权主体，维护唯一归属、解绑、转交与 OTA |
| 示例将令牌存入设备，现规格要求凭据仅留后端（§8.3；#10/#13） | 须明确授权流程由谁执行及如何安全交接；不能让设备仅提交一个用户 ID 就成为该用户 |

设备授权解决无浏览器登录，不证明当前 ESP32 固件已实现，也不证明同手机微信登录体验已通过。小智管理和语音服务仍需要设备可达的网络入口。

## 尚需确定或实测

- **退出的产品范围：** 现有要求是手机退出即停止对应 Key。共享应用授权撤销将停止同账号在本应用的多台设备；如果期望只停当前音箱，应另设单设备调用许可操作，不能复用账号授权撤销。需要明确“手机退出”是否仅指小智页面，以及收到外部 OIDC 注销通知时的范围。
- **自然到期的产品含义：** 建议浏览器自然到期不影响已经批准且仍有效的后台授权，以满足长期使用；小智本地登录期限、刷新无法恢复时的停用/重新授权策略，以及重新授权恢复哪些设备，需要写入最终验收，不能以“Key 没过期”代替决定。
- **真实配置：** 当前客户端是否已登记并获准 `offline_access`，回调、注销通知、两个账号、有效测试授权和 Ubuntu 入口仍需落实。公开 Discovery 支持不等于某个客户端已开通。
- **撤销可靠性：** 不同退出入口的通知覆盖、投递失败恢复、两种令牌失效后的撤销路径，以及旧授权与新授权的并发隔离需集市配合实测。
- **资源接口：** 新文档仍要求按模型/智能体详情调用，没有新增规范通 `answer` 增量/累计、结束/错误/取消样例，也未给出千问在集市的 TTS 型号、入口、流式与取消代理规则；沿用[接口资料](ai-market-api.md)中的待补项。

本次仅进行文档比较、公开 Discovery 读取和资料检查；没有执行登录、刷新、授权撤销、模型调用或设备操作。
