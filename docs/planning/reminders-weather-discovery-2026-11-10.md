## 用户提出的需求

1. 能通过语音设置日程，日程记录在服务器上，服务器定时提醒。
2. 寻找能替换固件中高德 API 的方法，支持定位并显示天气、温度、湿度、空气质量等信息。
3. 烧录固件时自动生成设备接入凭据，并在小智管理后台登记设备，方便识别。

用户本轮调用 `ask-matt` 选择工作流程。已采用 `grill-with-docs` 梳理产品行为，并用 `research` 查证天气与定位候选服务；本轮接续 `to-spec`、`to-tickets` 准备可评审的规格及任务拆分。

## 已核查的项目背景

- 调查基于 `origin/main` 的 `e00ff2a`，在独立任务分支 `docs/voice-reminders-weather-discovery` 中记录，不修改原工作区。
- 当前实机是 P4-01：Waveshare ESP32-P4 WiFi6 Touch LCD 4.3、P4 主控与 C6 Wi-Fi，不能沿用早期需求中 ESP32-S3 的硬件假设。当前固件 2.2.6 已恢复时钟、天气、日历首页；应用槽仅余 47,136 字节。镜像、源码基点与证据范围见 [P4 固件交接](../handoff/2026-11-10-device-firmware.md)。
- 服务端工程已有和风天气对话插件；语音查询天气、服务器定时主动播报和固件屏幕显示是不同链路，不能以其中一条存在推定其他能力已经完成。
- 正式设备控制 v1 已约定设备认证、状态同步、许可版本和退出停播，但该协议约定不等于当前实机已经实现它，见 [设备控制协议](../contracts/device-binding-v1.md)。新增提醒需要明确怎样与这些许可规则衔接。
- 原有对话记录保留及备份规则见 [产品规则](product-rules-2026-11-09.md)和 [ADR-0006](../adr/0006-exclude-conversation-content-from-backups.md)。本轮已单独确认日程的保留与备份规则，见下文 Q13 及 [ADR-0007](../adr/0007-back-up-schedules-as-business-data.md)。
- 本轮已发布日程规格 [#39](https://github.com/yanghan24/xiaozhi/issues/39)、环境规格 [#40](https://github.com/yanghan24/xiaozhi/issues/40)和六个实施任务 #41–#46，并同步总规格 #10、设备绑定 #13 及最终验收 #19。

## 新增：烧录时自动登记设备

用户在第二轮答复时追加此需求。它补充了 [设备控制协议](../contracts/device-binding-v1.md)中已经要求的预登记、独立设备接入凭据，以及尚待落实的物理写入和恢复流程。

目标是把逐台建档与凭据交付接入烧录操作，减少人工登记；设备识别与设备认证仍分别管理。现有协议规定 MAC、Client-Id、板型只能作标识或诊断，不可单独充当接入秘密；烧录登记也不能默认为客户账号绑定。

用户已确认首版流程：受控烧录工具联网连接后台，识别实际设备，取得逐台独立的凭据并写入设备持久存储，完成校验后记录交付结果；中途失败可安全重试。首版先做联网登记。当前 P4 工厂 MAC 与 C6 联网 MAC 不同，不能混用两者建立重复档案。

已只读核对 [#13](https://github.com/yanghan24/xiaozhi/issues/13) 当前正文：预登记及独立凭据、管理员补发、旧凭据作废和归属保留本已在范围内；批量建档与逐台写入的工艺仍是暂定。此次新增的是把这些步骤自动接入烧录，后续拆分应复用此边界，避免重复建立另一套设备准入。

只读代码调查确认：现有管理 API 的 `/device/register` 是旧六位激活码入口；`manualAddDevice` 会直接写运营用户/智能体关联，均不能当成产品预登记与独立凭据发行。固件当前 16 MB 分区布局仅有默认 NVS，启动修复及通用恢复路径存在整区擦除；另一个 32 MB 模板虽有 `nvsfactory`，但当前未启用且会移动应用及 assets。身份存储和正常重置保留必须单独设计验证，不能直接把秘密塞进普通配置区或直接切换分区模板。

## 后续工程约束

继续按已确认行为推进；供应商事实不能因免费无密钥偏好而默认公共免费服务允许面向客户使用。

日程实现应围绕已确认的账号/创建设备隔离、北京时间、语音复述确认及 10 分钟补播规则，设计持久化调度、设备待机通知、唯一投递标识、播放确认和跨重启恢复；重试不能让新归属收到旧内容。普通日程不自动承诺断网或断电仍准时送达，也不能以服务器已发出音频推定音箱已播放。

天气实现应采用已确认的中国大陆城市与自动/手动位置优先级，明确刷新、来源与观测/估算时间、缺值和缓存过期显示。IP 定位必须依据设备经可信网络入口观测到的出口 IP，不能把服务器自己的 IP 当作设备位置；网络代理可能使结果偏离设备所在地。完全替换高德需要修改固件环境服务，不能只改聚合 URL。当前快照的单一更新时间可能在天气失败时也更新，不能当作各项数据都已刷新。

供应商能力、授权与调用限制的查证记录见 [定位与天气替代调研](../development/weather-location-replacement-research.md)。目前查明 Open-Meteo 公共免费 API 仅限非商业用途；官方另提供不要求第三方 API Key 的自建路径，但服务器、存储、带宽和运维仍有成本。已同意先验证该自建候选及 350 台以上的承载方式，尚未部署或作出容量验收结论。

## 已确认的验收边界

共用现有高层边界：实际认证 HTTP、数据库/缓存、语音与设备协议；在已有 Ubuntu 环境执行后端和协议检查，并用真实 P4 确认首页、凭据保留和扬声器播放。自动回归可控制外部服务或时间；自建天气可行性必须实际读取公开数据，最终设备效果不能以 mock 或仅服务器合成代替。

容量目标：环境服务以 **350 台**作为本期验证目标，另以 **1,000 台**探索容量与扩容方式；用户已随任务拆分确认。覆盖同城缓存、多城市/网格、同时启动、冷/热缓存、缓存失效及上游更新失败，记录原始计数、耗时、CPU、内存、磁盘、带宽和限制；完整语音容量验收按同日确认的[50 路目标](product-rules-2026-11-09.md#50-路容量验收)执行，不因该环境服务测试而改成 350/1,000 路。

用户最终答复：“按此拆分，先纳入交付目标”。六项粒度、依赖、测试边界、容量探测与管理员授权工具后自动交付的流程均已批准；三项功能纳入既有 **2026-12-07** 交付目标。该日期是交付目标，天气可行性、实际资源和最终验收若受阻仍须如实报告，不能以计划日期替代通过证据。
