# #29 身份模块与 #13 产品绑定接入约定

2026-11-09 规格对齐。本文约定 #13 的后续实现，不声称现有 #29 已提供所有产品接口或状态。#29 的实现与可控外部回归已由 PR #31 交付，保持关闭；#28 已按环境与登记准备范围关闭，真实集市验收 #11 已按确认范围关闭，完整设备绑定属于 #13。证据见[模块回归](../verification/2026-11-09-customer-identity.md)和[真实身份验收汇总](../verification/2026-11-10-identity-acceptance-summary.md)。

## 1. 接口适配与兼容边界

| 层次 | 入口和响应 | #13 的责任 |
| --- | --- | --- |
| 已实现身份切片 | `/xiaozhi/customer/binding-flows`、`/binding-flows/{id}`；成功 `{data:...}`，失败 `{error:...}`；HTML 表单使用 303 | 保留已有页面、Cookie、CSRF 和流程关联，避免破坏已通过的真实登录 |
| 产品客户 JSON v1 | `/xiaozhi/customer/v1/`，按设备协议的 `version/code/data` 和 HTTP 状态 | 增加适配入口，复用同一身份服务和持久化，不重复实现授权码兑换或维护第二份会话 |
| 固定网页/回调 | `/xiaozhi/bind/{handle}`、`/xiaozhi/customer/oidc/callback`、`/xiaozhi/customer/oidc/backchannel-logout` | 保持实际已登记地址，不因 JSON 版本路径变化而更换 OIDC 回调 |

v1 必须适配创建流程和按当前浏览器查询流程，随后实现 confirm/open-account/sign-out 等产品操作。新增 v1 查询 `GET binding-flows/{flow_id}` 返回与身份切片相同的状态字段，并使用 v1 封装；这是对现有协议第 5 节的补全。

适配层只转换传输格式，不扩大权限。结果中的授权状态只说明当前授权链，不能凭旧 flow 的快照启用设备；操作前仍校验当前 generation、状态、客户会话及设备上下文。旧入口也不能绕过这些校验。

错误映射必须显式覆盖：缺少/失效客户身份 → `401 CUSTOMER_AUTH_REQUIRED`；身份流程不存在 → `404 FLOW_NOT_FOUND`；CSRF/跨来源拒绝 → `403 CSRF_REJECTED`；未知/过期设备请求 → 原 `REQUEST_NOT_FOUND` / `REQUEST_EXPIRED`；流程过期 → `410 FLOW_EXPIRED`；已消费流程/状态竞争 → `409 STATE_CHANGED`；上游临时错误 → `503 TEMPORARILY_UNAVAILABLE`。协议新增错误值同步 Schema。用户拒绝授权是流程结果 `IDENTITY_REFUSED`，不伪装成服务器失败。

#13 同时更新 Nginx 精确允许路径、页面调用、Schema/示例与 HTTP 回归。不能只加 `/v1/` 路径而遗漏 CSRF、错误封装或管理员隔离，也不能公开整个 `/customer/` 前缀。未明确废弃旧入口前保留兼容，不要求客户重新登记回调。

## 2. 身份确认与调用授权分开

现有 #29 在兑换身份时要求 Refresh Token 和业务 Key，任何步骤失败会使流程失败。#13 需扩展这一前置切片，以兑现 v1“身份有效但调用授权不具备仍可绑定”的已定规则，而不是把该规则从规格中删去。

- 身份有效必须完成 OIDC 签名/issuer/audience/nonce、state/PKCE、精确回调和 UserInfo.sub 一致性验证。缺少可信身份、客户拒绝授权、过期或重放时，不能建立归属。
- 身份已可信，但业务 Key 领取失败、缺少刷新能力或调用授权不具备时，应保留可信身份及明确的授权不可用状态。不得伪造 Key、制造 ACTIVE，或将一次网络错误描述为账号撤销。
- 首次 bind 可由手机明确确认并建立归属，保持 `blocked/market_auth_required`（未知刷新结果采用下一节的 pending）；不签发语音许可。resume 必须取得本次有效授权才恢复目标设备。
- 缺少模型或知识库资源权限或余额不阻止绑定，也不在绑定时额外提示资源余额；后续调用按实际响应处理，不能从一般 403 推断余额不足。
- 身份流程与当前授权的持久化分别表达，Key 缺失不可作为虚假的成功授权入库。新增路径必须保留 #29 的并发代际、通知先于回调、旧失败与新授权隔离保护。

## 3. 授权状态到设备行为

用户已确认 REFRESH_UNCERTAIN 暂停新调用并提示重新授权。下表是 #13/#14 要实现的消费约定，不是本次文档修改已经部署的行为。

| 状态 | 设备与调用行为 | 恢复条件 |
| --- | --- | --- |
| ACTIVE | 仅当设备原本有本地许可、准入和归属有效时允许调用；不能凭 ACTIVE 自动恢复已退出设备 | 正常刷新不改变已退出设备许可 |
| REFRESHING | 单次刷新进行中，不签发新的恢复许可；普通刷新过程本身不等于退出，不重发旧刷新请求；调用继续遵守现有有效授权和设备许可 | 同代际成功保存后回 ACTIVE，否则进入下面明确状态 |
| REFRESH_UNCERTAIN | 依赖该授权的设备进入 `blocked/market_auth_pending`，暂停新的模型/知识库/TTS 调用；保留归属及现有共享凭据；提示“授权待确认，请原账号重新授权”，不声称远端撤销 | 原账号重新授权成功后，只能显式恢复本次目标设备，不自动恢复其他停用设备 |
| REAUTH_REQUIRED | 当前授权链明确不可恢复，进入 `blocked/market_auth_required`；不继续凭尚可用 Key 调用，保留归属，不宣称已远端删除 Key | 原账号重新授权并确认本次目标设备 |

pending/required 都按既有许可版本传播、服务端输出闸门和设备停播 ACK 机制处理：不让旧结果或后续 TTS 输入绕过当前 blocked 状态；已被上游受理的请求可能继续执行/结算，不宣称远端取消。新状态出现时递增对应许可版本；旧刷新或旧通知不得回退新授权/新归属。`market_auth_pending` 已由 PR #26 提供相应实现；两端仍须遵守同版本 Schema/示例，完整产品验收归 #13。

普通尚未导致刷新结果未知的短暂网络错误，不凭一次错误撤销授权或改变归属。对于 REFRESH_UNCERTAIN，不自动重放旧刷新令牌、不自动删除 Key，也不无限期静默当作 ACTIVE。

浏览器通知使对应客户会话 `SESSION_ENDED`，与上述共享授权状态分别处理；没有独立授权失效证据时，不把浏览器退出转换成所有设备共享撤销。

## 4. 补充验收

1. 对新旧 JSON 入口执行真实 HTTP 过滤链验证：同一流程/浏览器、CSRF、错误映射、固定回调和拒绝路径一致；新入口满足 v1 封装。
2. 可信身份但业务凭证不可用：bind 可完成归属但不能发 voice/lease；resume 保持停用。可信身份本身失败或客户拒绝时不得绑定。
3. 同账号 A/B/C：A/B 使用该授权，C 已主动退出；刷新结果未知时 A/B 暂停新调用、旧输出不越过闸门，C 保持退出。状态和页面不能写成“集市已撤销”。
4. 原账号重登并确认 A，仅 A 恢复；旧刷新迟到结果不能误伤或启用 A/B/C。重启与多实例下结论相同。
5. OIDC 浏览器退出与共享授权撤销分别测试。#11 已验证真实后通道通知、第二独立账号及双账号退出隔离；[#11](https://github.com/yanghan24/xiaozhi/issues/11) 已按分层验收收尾，实际登记、通知及故障恢复的已验证和未覆盖范围见[最终报告](../verification/2026-11-11-identity-closeout.md)。

语音提供者按 #12 当前决定：本期接入 MCP 知识库，智能体需求留待后续，Edge TTS 默认；上述权限和输出保护同样适用于 Edge TTS，不因它不使用集市 Key 而绕过本地许可。
