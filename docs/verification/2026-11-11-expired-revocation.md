# #11 过期 Access Token 撤销拒绝验证

2026-11-11（香港时间），Ubuntu `jt@192.168.168.114`。用户指定继续使用此前同账号双机测试的账号，并确认就绪。本轮仅验证过期凭据的拒绝及现有授权保持，不执行有效凭据共享撤销。

## 版本与方法

- API 实查 `xiaozhi-product-api:1468eeb`。
- 专项工具为 PR #64 提交 `503ba27` 的 `revocation_probe.py`；Ubuntu 运行目录 `/home/jt/issue11-revocation-probe-20261111`，先前 10 项 loopback HTTP 测试通过。
- 从既有 B 设备停播 ACK 查询脚本定位设备，再经设备归属查询账号；恰好两台设备共享同一账号，当前授权 ACTIVE。没有选择另一历史登录账号。
- 在访问令牌有效时，核对 UserInfo、凭据返回的账号/应用及模型列表 200。将该枚旧令牌保存在服务器私有 0600 状态文件，不保存或重放 Refresh Token。
- 保持正常后台自动刷新，自然等待旧令牌过期；没有修改数据库到期时间、系统时钟或设备状态。
- 旧令牌到期时间为 15:23:17.508，观察结果时间为 15:23:41.520。先确认旧令牌 UserInfo 返回 401，再持久化单次尝试记录，并仅对 `DELETE /api/oidc/authorization` 发送一次旧令牌请求。

## 结果

| 检查 | 结果 |
| --- | --- |
| 旧令牌 UserInfo | HTTP 401 |
| 旧令牌授权撤销 | HTTP 401；未确认撤销成功，不重试 |
| 原业务 Key 模型列表 | HTTP 200；没有推理调用 |
| 当前授权 | ACTIVE，代际与基线一致 |
| 后台自动刷新 | 当前 Access Token 与旧值不同，到期时间已推进 |
| 新令牌 UserInfo | HTTP 200，主体与原账号匹配 |
| 设备 A | ready，许可版本 9，revision 17，前后不变 |
| 设备 B | ready，许可版本 9，revision 13，前后不变 |

因此本轮支持“过期 Access Token 的撤销请求被拒绝，原有效授权、Key 及两台设备服务端许可保持”。综合令牌、Key 和数据库观察得出结论，不以单一 401 或单一 ACTIVE 状态判定。工具通用结果仍为 `unconfirmed`，这表示未确认撤销成功；在本过期拒绝场景中，结合其他证据是预期结果。

[脱敏机器证据](evidence/2026-11-11-expired-revocation/result.json)记录上述结果。服务器准备/执行脚本为 `/home/jt/issue11-expired-prepare.sh`、`/home/jt/issue11-expired-execute.sh`。成功后删除含明文 Token/Key 的 `state.json` 及私有主体基线，保留无凭据的尝试、结果和证据文件。没有执行成功撤销，不需要通过重新登录恢复本次授权。

## 边界

这是实际网络、真实集市账号和自然过期令牌的拒绝验证；不是可控时间模拟。两台设备结果来自服务端许可状态，本轮没有要求用户现场问答或检查物理停播。

本轮不证明撤销端点 5xx/超时后的最终状态查询、幂等重试或重新授权恢复，也不覆盖真实刷新响应丢失。集市侧登记/批准范围、通知策略与历史 400 等仍在 #11 跟踪。#11 保持打开。
